# Sovereign manual Codex worker pilot — Issue #77

**Status: PROPOSED / unmerged.** This document and `.github/workflows/codex-manual-worker.yml` do not authorize a paid run, workflow publication, gameplay work, GitHub write privileges, an independent review, merger or deployment.

## Why this design

The owner reports a completed, manually triggered, read-only `openai/codex-action@v1` smoke test and an OpenAI Platform project called "Strategy game: Sovereign." That smoke-test report is **not independently verified in this issue**. This pilot is deliberately **one manual GitHub Actions worker and a local patch artifact**, not a standing autonomous coder. It does not change the existing cloud/local Codex paths, trusted main reporter, repository issue-status workflow, CI or branch protections.

It is limited to **Issue #76 Combat Prototype 1A** as an initial test. Future issue support requires separately reviewed source changes and authorization; merely changing the input does not allow arbitrary issues.

### Authorized execution boundary

1. Owner first separately authorizes Issue #76's **B/C implementation** and a **paid, single OpenAI Platform run**, identifies the current approved issue revision/scope and verifies absence of competing claims. The existence of this file, Issue #76, a label, a comment or a successful CI result does not constitute approval. Issue #77 approval does not authorize #76 work.
2. Owner independently checks Platform project spending and **enforced hard budget** status before each manual dispatch; inspect whether the project supports/enables a hard limit. The owner's preferences were **$50/month ceiling, $45 operational cutoff**. A project alert or manually typed acknowledgement **cannot enforce either ceiling**; the workflow has **no authoritative usage API** or trusted total-cost guard and must not be marketed as spend-capped. If usage, limit enforcement or remaining budget is unknown, do not run.
3. Owner selects **Actions → Sovereign Codex manual worker (candidate) → Run workflow**, branch `main`, issue number `76`, and types `APPROVE-76-ONE-PAID-RUN` only after the above checks. GitHub owner actor `MightyMulligan-ops` is hardcoded and all other actors, branches and issue numbers are rejected. This is **one paid invocation**, not permission for a repeat.
4. The job runs on a disposable Ubuntu runner, maximum 120 minutes, with repository `contents:read`, no persisted checkout credentials, no repository write token or production DB credentials passed to Codex. It installs frozen dependencies and generates the Prisma client **without DB access**. It then calls `openai/codex-action@v1` using the existing `OPENAI_API_KEY` secret and the sandboxed `:workspace` permission profile, with `drop-sudo`. The model may make local filesystem edits in the checkout; untrusted issue content is not interpolated into shell commands.
5. The agent is prompted to work on the small **pure two-formation deterministic combat engine only** and to run database-free checks. The action returns a final message and leaves changed local files. A separate non-privileged shell step verifies a bounded allowlisted file inventory, rejects renames, excessive change counts/sizes, and gathers a binary Git patch. The artifact is **untrusted code**: source diffs may contain prompt injections, so a trusted reviewer must inspect all changes, especially for security/privacy changes, secret-like contents and dependencies.
6. The job uploads one one-day-retention artifact with the patch, path list, source identity and final message. It does **not** commit, push, open a PR, edit issue labels or comments, dispatch additional agents, retry CI, mark ready, merge or deploy. Failed guardrails or Codex errors fail the run closed; no automatic fallback/paid retry.
7. The owner downloads the artifact, independently inspects and verifies it **without executing it blindly**. A later separate, explicitly owner-authorized P/D publisher (not present in this pilot) may apply an approved patch in a reviewed local environment, run validation and publish one draft PR to trigger the **unchanged fresh disposable PostgreSQL CI**. P/D are not supplied by artifact existence or dispatch. A full structured independent review follows before any owner E; F remains separate.

## Why this isn't a strict $45 / $50 cost cap

GitHub Actions `timeout-minutes` bounds runner wall clock, not API tokens or exact cost. The action's API usage may not map directly to the current project dashboard in real time. Project budget alerts may be delayed; the worker has no verified hard-budget API. Concurrency serializes worker runs but queues repeat manual dispatches rather than safely rejecting all duplicates. For these reasons a second dispatch **must not be submitted while one is queued/running**, and a meaningful money cap requires a separately audited trusted usage-check and/or verified platform-enforced hard limit. The intended $45 threshold is a **human operational stop**, not a software guarantee here.

## Security and availability constraints

- The workflow does not run on pull requests, labels, issue comments, pushes, schedules, workflow completion, bots, or `pull_request_target`. The protected workflow must be merged into `main` through normal independent review before it can be selected manually.
- Only `MightyMulligan-ops`, on `refs/heads/main`, with exactly issue `76` and typed confirmation passes the job's gate. The issue scope is held in this trusted-main document, not dynamically taken from issue text. The owner still verifies actual B/C authorization and frozen issue scope manually.
- The worker cannot publish to GitHub. It may have local workspace write permissions, which is not the same as production code authorization. GitHub artifacts and final messages are untrusted; automated file/path checks are necessary but not sufficient.
- The Codex action needs the OpenAI API key as a secret. Its proxy/security design and the `:workspace` profile are described by the action's official repository. A worker still processes untrusted repository code and cannot be assumed immune to all exfiltration techniques. No API key or token values belong in the artifact.
- No live or existing database, Docker/PostgreSQL startup, migrations, CI workflow modifications, backend production wiring, external agents or deployment are authorized. The worker gets no write-token. If any needed capability is unavailable, it must stop rather than weaken isolation.
- No formal job result, spending data, action version pin audit or real end-to-end dry run has been obtained for this unmerged candidate. Validation requires independent static review, existing PR CI, owner billing verification, and one separately approved deliberate pilot dispatch after merge.

## Source-bound combat brief for the fixed pilot issue

Issue #76 is **Combat Prototype 1A**, a pure, deterministic two-hostile-formation battle engine. Start with exactly one Lieutenant plus Infantry per formation. ATK/DEF are damage **output**, not mitigation. Sequential exchanges apply simultaneous damage; mutual death is possible; persistent HP continues until the encounter ends, then surviving units heal. Leaders are protected until combatants die; leaders cannot keep combat active. Include bounded deterministic seeded rolls, roles, tests and a server-only audit. Refuse unsupported multi-army/multi-faction/diplomacy/air/naval/recruitment rules. Never invent final balance numbers or write to production transport or database. Preserve existing game engine and source contracts.
