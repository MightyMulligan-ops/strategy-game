# Authoritative starting armies — 006D.1 / Issue #49

Implementation is prepared on one local issue branch and remains unmerged. This milestone initializes durable armies and reads them; it executes no orders, movement, Ready, closure, freezing, resolution, advancement, encounters or combat.

## Creation-time cohort and atomic start

Production composition in `apps/server/src/index.ts` explicitly supplies `INITIAL_ARMIES_RUNTIME_PROFILE` to the trusted fourth `LobbyRepository` constructor argument. This selects ruleset `initial-armies/1`, simulation `initial-armies-v1`, and the existing provisional tie-policy metadata. Client input has no runtime selector. The repository's default remains `initial-world-v1` for existing callers/fixtures. Neither constructor nor start changes an existing configuration. Unpinned and old pinned OPEN/RUNNING matches retain their exact behavior; there is no upgrade/backfill/repair operation.

Host start holds the existing parent Match lock, verifies host and ready active roster, classifies immutable pins, generates/stores the unchanged `territory-grid-v1` archive (production side 5), and derives the complete deterministic army plan before sampling the trusted opening clock once. It inserts snapshot, OPEN Turn 1, revision-zero unready empty drafts and INITIAL history, then transitions RUNNING in the same transaction. Acknowledgement follows commit. Retry on RUNNING never regenerates or repairs. Deferred SQL checks require the whole bundle; all new-runtime artifacts become immutable. Existing parent-delete cleanup is preserved with cohort-specific cascade ordering.

## Contracts, identity and restoration

Server-only snapshot v3 / `initial_armies` uses the existing `GameSnapshotRecord.payload`, not new mutable tables. It binds config, canonical active roster, immutable world reference, fixed policy, units and formations. `startingState.units` in the archived world remains empty. Public world DTOs and the generator are unchanged.

Every active player has exactly one formation at their existing capital city coordinates, one Infantry-specialized Lieutenant and five individually identified Infantry. Each unit has schemaVersion, unitId, match-local ownerPlayerId, kind and permanent originalSpawnNodeId; the Lieutenant also has rank/specialization. Formation schemaVersion, formationId, ownerPlayerId, ordered unitIds and position are authoritative; unit positions derive from membership. There are no combat statistics. Six unique members have exactly one membership and consistent owner/source. At most 40 formations / 240 units are accepted.

IDs use SHA-256 of canonical `{version,matchId,playerId,worldRef,sourceNodeId,slot}`. Version is `initial-armies-v1`; slots are `lieutenant`, `infantry-1` through `infantry-5`, and `capital-formation`. Prefixes are `unit:` and `formation:` with exactly 64 lowercase hex digits. Players sort with code-point ID comparison; units sort by ID within each player; formations follow player order. IDs use no account/provider identity, sequence, client ID, random/time input or locale. Spawn provenance is the owner's existing capital Military Supplies node and must never reset on future travel or capture.

Snapshot ID is `initial-armies:` plus SHA-256 over canonical `{snapshot:<all metadata except snapshotId>,runtimeProfile}` using existing canonical JSON encoding. Opening time is lifecycle data and does not change army identity. Restore parses actual persisted contents, validates the actual archive and metadata, regenerates the pure expected plan and compares the entire canonical payload, including IDs, composition, coordinates, provenance, roster and hashes. GET does not regenerate stored data, write or repair. Missing/corrupt new-profile data fails closed. Hash syntax alone is insufficient integrity.

## Read boundary and map

`GET /api/matches/:matchId/formations` accepts only optional `schemaVersion=1`. It requires a valid signed persisted session, registered username and active membership before private metadata/snapshot retrieval. A read-only RepeatableRead transaction yields a consistent view without observing time, acquiring write locks or mutations. Outsider/inactive/missing use the same NOT_FOUND response. Existing rate limits and no-store/no-referrer/nosniff headers apply. No Origin/CSRF check is needed for GET; mutation routes are not introduced.

The explicit DTO contains only the caller's formation ID, match-local owner, position and six own unit IDs/types/spawn references plus Lieutenant rank/specialization. Host has no extra access. No enemy formations, raw snapshot, seed, digest, policy, draft or account/session/provider ID is transmitted. Availability is NOT_STARTED (OPEN), UNINITIALIZED (legacy RUNNING), UNSUPPORTED (validated old initial-world), or READY. Corrupt/unknown pinned state returns sanitized INTERNAL_ERROR rather than an empty army.

React fetches this projection independently only alongside a matching READY world. Refresh/world/match/session changes clear private state, abort reads and ignore stale responses. A nonfocusable diamond is centered at the exact capital position; native HTML details/list inspection shows “Lieutenant + 5 Infantry”, members and provenance. Existing SVG one-Tab-stop roving territory focus, arrow navigation, capital stars and text remain available. The marker adds no competing map focus target. Loading, unavailable, denied and malformed states offer explicit refresh only, no polling or command controls. Browser-level screen-reader/manual dense-map acceptance remains a separate owner review.

## Pure helpers and deferred policy

Coordinates reuse integer map points (global 0..4900); movement input additionally validates world width <=4900 and height <=4200 and actual bounds. Euclidean distance and exact squared distance are pure. Leadership rejects duplicate IDs/ranks and derives General > Colonel > Captain > Lieutenant without assigning initiative. Starting-foot eligibility accepts only supported Infantry/Lieutenant units with one owner; each proposed numbered segment contributes to a single cumulative 250 map-unit budget. Exactly 250 is eligible, over 250 is not. Helpers return facts, never commands, spending or mutation.

Five leaderless Infantry require a leader; one leaderless Infantry returns SOURCE_RADIUS_UNAPPROVED even at distance zero. Policy pins `leaderlessRadius:null`; this runtime has no executable source-radius exception. Future approval must separately define the radius and enforce the permanent original node. No mixed-unit formula, terrain modifier, collision epsilon or formation radius is supplied.

Encounter classification requires an explicit authoritative friendly/hostile/unknown relationship. Foreign ownership does not establish hostility. Exact same-point or supplied same-city contact can classify friendly co-location, hostile occupied destination or contested point/city; unknown relationship, nonexact contact, crossing paths and vacating positions require policy. No timing, interception, defender, damage or encounter result is produced. The approved future hostile-convergence intention is an unresolved encounter blocking both opposing stacks at their last valid positions; execution requires a separate runtime/design.
